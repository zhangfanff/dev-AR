# 同一帧串行/并行实验

版本：1.4-same-frame-parallel，versionCode 6。项目 `G:\AndroidStudioProjects\CabinetMatcherCamera`，包名及离线模型不变，仍然只使用 CPU。

## 使用

1. 安装新版 ARM64 APK，在顶部选择 YOLO 尺寸、OCR 模型。
2. 执行模式默认“串行（原流程对照）”，可在暂停识别后切换为“并行（YOLO＋OCR＋手部）”。每次点击开始，更新率和去除本次首帧的平均耗时重新统计；上次实际使用的模式自动保存。
3. 使用相同模型、视频分析尺寸、OCR 长边、匹配设置和静止场景对比。每种模式等待多帧，主要比较“后续帧均值：处理”和结果更新率。保持柜子、手部数量相近，交替重复测试，减少发热、手部跟踪状态变化等影响。
4. JSON 导出同时记录 execution.mode、同帧约束、线程设置、frame_id 与分阶段毫秒数。PNG 和实时预览的框、骨架都来自同一完成帧。

## 执行依赖

串行：文字检测 → YOLO → 几何匹配 → 匹配区域方向判断/文字识别 → 手部检测 → 标注。

并行：

```text
同一张方向纠正后的 BGR 帧
    ├─ YOLO 工作线程：预处理 → YOLO → 后处理 ─────────────┐
    ├─ OCR/协调线程：整图文字检测 ───────────────────────┤
    │                       等待 YOLO + 文字检测完成 ←──┘
    │                       几何匹配 → 匹配区域方向判断与文字识别 ──┐
    └─ 手部工作线程：独立位图转换 → MediaPipe 手部关键点 ─────────┤
                                             全部完成后汇合 ←──┘
                                             生成标注与结果 → 发布
                                             关闭当前 ImageProxy
                                             取下一张最新可用帧
```

OCR 识别不必等手部检测完成，但必须等 YOLO 和文字框都完成，才能知道要识别哪些文字区域。已匹配区域仍按顺序做文字方向判断和识别，避免同一个识别会话被多个任务同时使用。

若各任务速度完全不受并发影响，忽略转换和绘制开销，串行耗时近似 `D + Y + R + H`，并行近似 `max(max(D,Y)+R, H)`；D 为文字检测，Y 为 YOLO，R 为匹配和已选文字识别，H 为手部。此式只是依赖关系的理想估算，真实并发任务会争用 CPU 和内存带宽。

## 帧与资源所有权

- CameraX 仍为 KEEP_ONLY_LATEST，FrameGate 限制“一帧在处理”。没有把视频帧提交进多个队列同时处理。
- OCR/协调线程、YOLO 工作线程、手部工作线程各为固定单线程 executor。每个 ONNX 会话仍设置 intra-op=2、inter-op=1，与串行模式一致；手部仍使用 MediaPipe CPU。模型内部也可能使用多线程，应用线程数不等于所有原生线程数。
- BGR 帧只读共享，预处理结果由各任务独立持有。手部使用独立 Bitmap，避免 MediaPipe 的图片生命周期影响标注图片。
- MediaPipe 初始化、重置、检测、关闭始终在同一手部线程上。换会话会重置手部跟踪器；该开销在首帧单独计时。
- 不对原生推理任务调用 Future.cancel(true)。暂停、关闭、切模型通过 generation 判定使旧结果失效；finally 仍会等待所有已经提交的分支真正退出，再释放 BGR/ImageProxy。某个任务失败时同样等待其他任务退出。
- 新模型替换与销毁在协调线程排队，位于当前帧所有分支汇合之后；不会提前关闭仍在使用的模型。旧会话结果不发布。

## 耗时口径

- yolo.total、ocr_detection.total、text_loop.total、hands.total 为各模块在其工作线程上的实际经过时间，包含与其他任务竞争资源产生的等待，不是 CPU 使用时间。
- detection.wall 是启动检测阶段至 YOLO 与文字检测全部完成的时间。并行模式应比较这个值，而不是把 yolo.total 与 ocr_detection.total 相加。
- pipeline.total 是柜体路径的实际耗时，包括等待 YOLO、匹配及识别；不含等待手部结束。pipeline.other 用 detection.wall 计算，避免把重叠时间重复减去。
- hands.bitmap 是手部独立输入位图转换；hands.model_reset 是跟踪器重置；hands.inference 为同步手部推理与结果整理；hands.total 包括这些步骤及清理。
- combined.total 是从启动模型分支到所有分支完成、生成快照和合并标注的实际耗时。camera.processing 还包括输入帧转换。界面“本帧处理”与“后续帧均值：处理”采用整帧墙钟时间。
- 模型加载在帧外。首帧可能包含首次内核准备、方向模型首次加载、手部跟踪器重置等，不能用单张首帧比较。

并行后某个模块显示耗时更长是可能的，判断是否有收益应看整帧时间和更新率。并行不消除相机移动导致的历史帧结果滞后；仍没有运动补偿或柜体跟踪。

## 对照与回退

在同一新版 App 内选择“串行”即可对照。旧版 1.3.1 APK 与源码 ZIP 保留在交付目录，名称含 `outside-center`；新版文件名称含 `parallel`。新代码没有更换模型、匹配扇区规则或文本中心排除规则。

验证结果见 [VALIDATION_PARALLEL.md](VALIDATION_PARALLEL.md)。手机当前未连接，模拟器结果只能证明功能和并发兼容性，不能用于判断手机加速幅度。
